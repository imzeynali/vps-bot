# معماری ربات

ربات از سه لایه‌ی مستقل ساخته شده است. جهت وابستگی همیشه **یک‌طرفه** است:

```
bot/ (رابط تلگرام)  ──►  lib/ (منطق کسب‌وکار)  ──►  datacenters/ (اتصال به دیتاسنترها)  ──►  core/ (هسته‌ی پایه)
```

## 1) Base core — `src/core/`
هسته‌ی پایه؛ هر چیز مشترک و **مستقل از دیتاسنتر** اینجاست. هیچ‌چیز در core به دیتاسنتر خاصی وابسته نیست.

| فایل | کار |
|---|---|
| `config.ts` | تنظیمات محیطی (`.env.local`): توکن، ادمین‌ها، `virt.*`، `cgi.*` |
| `db.ts` | اتصال PostgreSQL، `query`، `queryOne`، `withTx` |
| `settings.ts` | تنظیمات قابل‌ویرایش از پنل ادمین (جدول `settings`) |
| `state.ts` | state گفتگوی هر کاربر |
| `flags.ts` | پرچم‌های روشن/خاموش (مثلاً روشن بودن دیتاسنتر در منوی خرید) |
| `errors.ts` | `NotReadyError`، برچسب‌گذاری خطا با شناسه‌ی دیتاسنتر |
| `logger.ts` | لاگ برچسب‌دار `[scope]` |
| `password.ts` | ساخت پسورد |
| `index.ts` | ورودی واحد: `import { query, config } from "@/core"` |

مسیرهای قدیمی `src/lib/{config,db,state,settings}.ts` فقط shim سازگاری هستند.

## 2) دیتاسنترها — `src/datacenters/`
هر دیتاسنتر یک پوشه‌ی مستقل دارد و اینترفیس `DatacenterProvider` (فایل `types.ts`) را پیاده می‌کند.

```
datacenters/
  types.ts          قرارداد مشترک
  registry.ts       ثبت و جستجوی دیتاسنترها، روشن/خاموش، تشخیص دیتاسنتر هر سرویس
  index.ts          ثبت همه‌ی دیتاسنترها (نقطه‌ی افزودن)
  virtualizor/      🇮🇷 ایران (api.ts = کلاینت پنل، service.ts = منطق سرویس، index.ts = provider)
  cgi/              🌍 بین‌الملل — HostVDS/OpenStack (http.ts = Keystone+HTTP، openstack.ts = Nova/Neutron، seed.ts = ورود کاتالوگ)
```

**قوانین جداسازی**
- کد یک دیتاسنتر هرگز دیتاسنتر دیگر را import نمی‌کند (فقط `core` و `types`).
- هر ردیف `services`، `plans`، `locations`، `os_templates` ستون `datacenter` دارد (پیش‌فرض `virtualizor`). کاتالوگ هر دیتاسنتر جداست و خرید با ناسازگاری دیتاسنتر رد می‌شود.
- `src/lib/provider.ts` مسیریاب است: هر عملیات (ساخت/روشن/ریبیلد/حذف) به دیتاسنترِ همان سرویس می‌رود. `provisioning/billing/trial` از همین مسیریاب استفاده می‌کنند و چیزی از Virtualizor نمی‌دانند.
- خطای هر دیتاسنتر با شناسه‌ی آن علامت می‌خورد و در تاپیک «خطا» با نام دیتاسنتر گزارش می‌شود؛ به دیتاسنتر دیگر سرایت نمی‌کند.
- بازیابی سرویس‌های گیرکرده برای هر دیتاسنتر جدا انجام می‌شود؛ دیتاسنترِ خراب فقط خودش را عقب می‌اندازد.
- خاموش کردن یک دیتاسنتر (پنل ادمین ← 🌐 دیتاسنترها) فقط از منوی خرید حذفش می‌کند؛ سرویس‌های موجود (مدیریت، صورتحساب، حذف) دست‌نخورده کار می‌کنند.

## افزودن یک دیتاسنتر جدید (مثلاً تکمیل CGI)
1. در `src/core/config.ts` تنظیمات محیطی دیتاسنتر را اضافه کنید (برای CGI از قبل هست: `CGI_API_URL`, `CGI_API_KEY`).
2. در `src/datacenters/<id>/index.ts` متدهای `DatacenterProvider` را پیاده کنید و `implemented: true` بگذارید:
   `provision / power / rebuild / remove / refreshIp / health / isDefinitiveFailure / removeOrphan / findExisting`.
3. اگر دیتاسنتر جدید است، آن را در `src/datacenters/index.ts` با `registerDatacenter(...)` ثبت کنید.
4. لوکیشن، سیستم‌عامل و پلن‌های آن دیتاسنتر را با `datacenter='<id>'` در جداول کاتالوگ بسازید. جریان خرید (لوکیشن ← OS ← پلن ← پرداخت) بدون تغییر کار می‌کند.
5. `npm test` را اجرا کنید (تست‌های ایران نباید تغییری کنند).

> نکته: `isDefinitiveFailure` مشخص می‌کند خطای ساخت «قطعی» است (بازگشت وجه خودکار) یا «نامشخص» (مثل timeout؛ سرویس در provisioning می‌ماند و `findExisting` بعداً بررسی می‌کند).

## تست‌ها
```
npm test          # هر سه مجموعه
npm run test:virt # ساخت/صورتحساب/بازگشت وجه روی پنل شبیه‌ساز
npm run test:admin
npm run test:dc   # جداسازی دیتاسنترها
```
(نیاز به `DATABASE_URL` یک PostgreSQL تست دارد.)

## دیتاسنتر CGI (HostVDS / OpenStack)
- **احراز هویت:** Application Credential (Keystone v3)؛ یک توکن برای همه‌ی ریجن‌ها؛ ۵ دقیقه قبل از انقضا یا با ۴۰۱ تمدید می‌شود. آدرس سرویس‌ها از کاتالوگ توکن (به‌ازای ریجن) می‌آید.
- **چندریجنی:** هر لوکیشن منو (پاریس/هلند/لاتویا/فنلاند) یک ریجن است (`locations.dc_ref`). ریجن و شبکه‌ی انتخابی هر سرویس در `services.dc_meta` = `{region, network, network_id, port_id}` ذخیره می‌شود و همه‌ی عملیات بعدی (روشن/خاموش/حذف) روی همان ریجن انجام می‌شود.
- **نام به‌جای شناسه:** پلن (`plans.dc_ref` = `hostvds-1`) و سیستم‌عامل (`os_templates.dc_ref` = `Ubuntu-24.04-amd64`) با نام ذخیره می‌شوند و در هر ریجن به شناسه‌ی همان ریجن تبدیل می‌شوند. پلنی که در یک ریجن نیست در منوی آن لوکیشن نمایش داده نمی‌شود.
- **منوی خرید (`buyCgi.ts`):** لوکیشن (پرچم) ← سرویس (قیمت‌ها) ← سیستم‌عامل ← شبکه (رنج آی‌پی) ← پهنای باند ← نوع پرداخت ← ساخت و تحویل. هر مرحله ورودی را دوباره اعتبارسنجی می‌کند.
- **پهنای باند و قیمت:** جدول `bandwidth_prices` (به‌ازای پلن و سرعت ۱۰۰/۱۰۰۰/۱۰۰۰۰) قیمت «تمام‌شده»ی سرویس را نگه می‌دارد. هزینه‌ی کسر اول، `services.hourly_price` و `services.monthly_price` از روی سرعت انتخابی تعیین می‌شوند (نه قیمت پایه‌ی پلن)، پس صورتحساب ساعتی/ماهانه خودکار همان را کسر می‌کند. پلن CGI بدون قیمتِ پهنای باند فروخته نمی‌شود. قیمت‌ها با `/setbw` و `/bw` (ادمین) مدیریت می‌شوند. اعمال واقعیِ محدودیت سرعت اختیاری است: اگر برای یک سرعت `qos_ref` (شناسه‌ی QoS policy در Neutron) ثبت شود، هنگام ساخت پورت اعمال می‌شود.
- **ساخت سرور:** ۱) پورت روی شبکه‌ی انتخابیِ کاربر (بدون `fixed_ips`؛ سیاست Neutron آن را ممنوع کرده) و تأیید اینکه IPv4 گرفته ۲) سرور با همان پورت (Nova) ۳) انتظار تا ACTIVE. اگر شبکه‌ی انتخابی ظرفیت نداشته باشد، شبکه‌ی دیگری جایگزین نمی‌شود: خطای قطعی + بازگشت وجه + راهنمای «شبکه‌ی دیگری انتخاب کنید».
- **پسورد root:** با cloud-init (`user_data`).
- **idempotent:** نام سرور `tcg-<serviceId>`؛ اجرای دوباره/بازیابی همان را پیدا می‌کند. سرورِ گیرکرده در BUILD پاک می‌شود (هزینه‌ی بی‌صاحب نمی‌ماند).
- **حذف:** سرور ← انتظار تا ۴۰۴ ← حذف پورت (پورتِ ساخته‌ی خودمان با حذف سرور پاک نمی‌شود).
- **خطای قطعی** (بازگشت وجه): ۴xx جز ۴۰۱/۴۰۸/۴۲۹، ERROR، تنظیمات ناقص، سهمیه/آی‌پی پر. **نامشخص:** timeout، ۵xx، قطع اتصال.
- **کاتالوگ:** `npm run cgi:seed` فلورها، Ubuntu 20/22/24 و ۴ لوکیشن را می‌ریزد (`CGI_REGION_MAP` نگاشت ریجن). فقط `hostvds-1/2/4` فعال و قیمت‌دار می‌شوند؛ قیمت‌های ادمین بازنویسی نمی‌شود.
- **ابزارها:** `npm run cgi:regions` (ریجن‌ها و کشور تقریبی)، `npm run cgi:smoke -- create [os] [region] [network]` (سرور واقعی) و `... delete <id>`.
- Cinder و Floating IP استفاده نمی‌شود.
